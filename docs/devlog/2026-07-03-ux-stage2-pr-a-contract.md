## Контракт payload

**`breadcrumb` строки — полная цепочка, позиционный пересчёт, не разбор `embedding_input`.**
Роадмап предлагал деривацию из `embedding_input` (хрупко — в названиях есть точки). Вместо этого
бэк на чтении пересчитывает цепочку предков тем же алгоритмом, что парсер: `resolve_ancestor_indices`
по `depth` в порядке `source_index` (новая `full_breadcrumbs` в
[classification.py](../../backend/app/domain/classification.py)). UI-крошка — **полная** цепочка,
включая org-узлы: оператор смотрит на смету в Excel, где org-разделы видимы, — крошка зеркалит
документ, а не org-free вход эмбеддера (у отображения другой потребитель, чем у эмбеддинга).
`GET /estimates/{id}` отдаёт `breadcrumb` каждой строки; PATCH-ответ строки его не пересчитывает
(нужны все строки сметы) — см. ниже про гидратацию.

**Крошки статей — через дерево `parent_id`, не через `embedding_input`.** Новый порт
`ancestor_names_by_ids` ([ports.py](../../backend/app/domain/ports.py),
[catalog_tree.py](../../backend/app/domain/catalog_tree.py)) строит цепочки имён предков статьи
по честному дереву `template_articles.parent_id` — надёжный источник (дерево мелкое: 2–3 уровня,
362 статьи, один проход по загруженной карте `id → (name, parent_id)`, без рекурсивных запросов).
Используется для `matched_breadcrumb`/`final_breadcrumb`/`candidates[].breadcrumb` в
`EstimateRowOut` и для `breadcrumb` в ответе `GET /articles/search`. Кандидат/результат поиска
без `id` (статья удалена из справочника) — пустой список, graceful fallback.

**`source_index`/`match_error`.** `EstimateRowOut` дополнен `source_index: int` (порядок исходного
документа сметы — для будущей полосы контекста PR-B) и `match_error: str | null` (текст ошибки
`error`-строк — для карточки PR-B). Пробрасываются из домена/репозитория без пересчёта.

**`final_breadcrumb` — выбор через поиск, не подмножество кандидатов.** Когда оператор выбирает
статью через ручной поиск (а не из топ-3 кандидатов), финальная статья может не входить в
`candidates` — её крошка резолвится отдельно тем же порталом `ancestor_names_by_ids`, а не
выводится из уже посчитанных крошек кандидатов.

**PATCH гидратирует крошки статей строки; breadcrumb строки PATCH не несёт.** `PATCH
/estimates/{id}/rows/{id}/review` пересчитывает `matched_breadcrumb`/`final_breadcrumb`/крошки
кандидатов ОДНОЙ строки (дёшево — дерево статей уже загружено), но НЕ пересчитывает `breadcrumb`
самой строки сметы (для позиционного резолва нужны все строки сметы, PATCH их не грузит).
Фронт (`rowFromDto(dto, prev)` в [estimates.ts](../../frontend/src/lib/api/estimates.ts))
компенсирует это на слиянии: **единственная merge-ветка — `breadcrumb` строки** (PATCH шлёт `[]`,
проверка по длине, а не `??`, иначе пустой массив затёр бы `prev`). Крошки статей
(`matchedBreadcrumb`/`finalBreadcrumb`/крошки кандидатов) **не мержатся** — PATCH их гидратирует
сам, а `final_article_id` меняется этим же PATCH-ем: наследование из `prev` подставило бы крошку
ПРЕЖНЕЙ статьи под НОВУЮ. Закреплено пин-тестом «переигрывание решения не наследует
`final_breadcrumb` без ключа в ответе» ([estimates.test.ts](../../frontend/src/lib/api/estimates.test.ts)).

## Контракт excluded (текущая таблица, до карточки)

- `MatchStatus` расширен до полного множества статусов бэка: `+ "pending" | "excluded"`
  ([lib/types.ts](../../frontend/src/lib/types.ts)).
- `statusTone` в `ReviewRow.tsx` — exhaustive `Record<MatchStatus, string>`: добавление статуса
  бэка без ключа здесь роняет компиляцию, а не тонет молча в `?? ""`.
- Очередь хоткеев в `ReviewScreen.tsx`: `rows.filter(r => r.status !== "confident")` →
  `rows.filter(requiresDecision)` (позитивное зеркало бэкового `_REVIEWABLE`, введённого фиксом
  PR #20) — excluded/pending/фонд-хиты выходят из клавиатурной навигации.
- `statusLabel()` отдаёт «Контекст» (excluded) / «В обработке» (pending) ДО веток по решению
  оператора — контекстные строки не решаются в ревью, их `decision` вечно `pending`.
- Excluded/pending-строки в таблице: `opacity-60`, лейбл в `Badge`, `expandable = !contextRow` —
  не раскрываются в аккордеон кликом.
- Шапка «N строк СМР» сознательно НЕ тронута этим PR — отдельный вопрос PR-B/дальше.

Гасит пункты TECH_DEBT «Этап 1 UX-роадмапа: полировка из ревью» про тип `MatchStatus` и очередь
хоткеев/`statusLabel` (см. правку TECH_DEBT этим же коммитом).

## Страж-проекция (`test_breadcrumb_guard.py`)

Новый тест-страж — не equality-тест, а **проекция**: пересчитанная позиционным резолвом полная
цепочка → отфильтровать предков со статусом `excluded` → `". ".join(filtered + [name]) ==
embedding_input`. Ценность — верификация позиционного резолва (`resolve_ancestor_indices`,
машинерия, где раньше жил баг коллизии дублей кодов, PR #16) против того, что реально записал
классификатор в `embedding_input`, а не переизобретение конвейера крошки (org-фильтр, leaf-rescue)
на стороне UI. Прокси-инвариант «`status == excluded` ⇔ предок ORG»: спасённый org-лист (ORG-класс,
`excluded=False`) — всегда лист и предком не бывает; если бы org-классификация влияла на крошку,
не оставив следа в статусе, страж бы упал (полезная находка, не поломка). Excluded-строки
сознательно ВНУТРИ инварианта — доказано на пайплайне (`save_node_classifications` пишет
`embedding_input` безусловно всем строкам прохода) и на живых данных dev-БД (org-заголовки несут
org-free крошку без собственного имени). Вне инварианта — только `pending` (сырой парсерный join
до классификации). В тесте — комментарий-предохранитель: при изменении формата `embedding_input`
(например, unit/quantity из таблицы решений роадмапа) править проекцию/сравнение здесь, а НЕ
`full_breadcrumbs`/UI-пересчёт — полная UI-цепочка от формата эмбеддера не зависит.

Прошла с первого запуска, 5/5 — пин существующего поведения, подгонки фикстур не потребовалось;
ревьюер плана доказал байт-дифф рукописных crumb-ов с планом до реализации.
