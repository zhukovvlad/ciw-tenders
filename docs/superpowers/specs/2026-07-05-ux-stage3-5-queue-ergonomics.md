# UX этап 3.5: эргономика карточки очереди

**Дата:** 2026-07-05
**Статус:** дизайн согласован (внешнее дизайн-ревью макета 2026-07-04 + верификация по коду), ждёт ревью спеки
**Родитель:** [2026-07-02-ux-roadmap-design.md](2026-07-02-ux-roadmap-design.md) (внеплановый мини-этап между 3 и 4);
семантику полосы контекста задал [2026-07-03-ux-stage2-review-screen-design.md](2026-07-03-ux-stage2-review-screen-design.md) §3b.
**Скоуп:** пять правок экрана очереди ревью (`ReviewScreen` / `ReviewCard` / `ContextStrip`).
Два PR: PR-1 — косметика без изменения поведения, PR-2 — семантика границы раздела в полосе.
Без новых компонентов, без изменений контракта payload, без бэка.

## 1. Контекст: дизайн-ревью очереди

Внешнее дизайн-ревью (макет 2026-07-04) разобрало экран очереди после этапов 2–3.
Замечания сверены с кодом; каждое подтвердилось:

- **Зона решения тянется во всю ширину монитора** — карточка и полоса рендерятся
  в `flex flex-col` без ограничения (`ReviewScreen`). Глаз ходит слева направо
  через весь экран вместо одной зрительной колонки сверху вниз.
- **Полоса контекста стоит после карточки** — окружение («до меня
  электрооборудование ушло в 10.8.3, узлы учёта в 10.8.4») оператор видит
  *после* списка кандидатов, хотя аргумент, которым полосу вводили (спека
  этапа 2 §3b), — подтверждение кандидата соседями — работает *до* чтения списка.
- **Крошка кандидата прижата к правому краю** — при одноимённых кандидатах
  («Пусконаладочные работы» × 4) различающая информация живёт там, куда глаз
  доходит в последнюю очередь; правый край стал вторым столбцом для чтения.
- **«Завершить» всегда primary** — на середине очереди кнопка выглядит как
  приглашение, а по нажатию ругается диалогом «остались нерешённые строки».
- **Граница раздела в полосе** — неподписанная линия по `breadcrumb[0]`
  (самый верхний уровень). В реальном сценарии макета (два подраздела под одним
  верхнеуровневым «Инженерные системы») граница не отрисуется вообще, а ловушка
  «лукавого соседства» одноимённых работ живёт именно на уровне подразделов.
- **Активная строка полосы дублирует статус** — `rightSide` выводит «требует
  проверки» для строки, которую оператор прямо сейчас решает.

Не переносится из макета (помечено самим ревьюером): 3 кандидата вместо 5 —
упрощение макета; «Без пары» в один ряд с поиском — отложено до телеметрии.

## 2. Ключевые решения (и почему)

| Решение | Обоснование |
|---|---|
| Зона решения — центрированный контейнер `max-w` (ориентир ~1100px, значение подбирается вживую); тулбар и легенда полноширинные | Всё нужное для решения — в одной зрительной колонке, глаз ходит сверху вниз. Тулбар и легенда — рамка, не содержание. |
| Полоса контекста переезжает внутрь карточки, между заголовком работы и кандидатами — слот-проп `contextStrip?: ReactNode` в `ReviewCard` | Порядок чтения повторяет логику решения: крошка → строка → окружение → кандидаты → запасные выходы. Слот, а не прямой рендер: полосе нужны `state`/`activeRowNumber`, которых у карточки нет, — карточка остаётся в неведении о ревью-стейте. Отвергнуто «полоса выше карточки снаружи»: крошка и заголовок работы должны стоять НАД окружением. |
| Крошка кандидата примыкает к имени (вторичным стилем), вправо уходит только score | Одноимённые кандидаты различаются при чтении имени, правый край перестаёт быть вторым столбцом. Шаблон один на кандидатов и синтетическую рекомендацию (общий `candidateButtonClass`). |
| «Завершить»: `variant="outline"` при `pending > 0`, primary при `pending === 0` | «Кнопка приглашает, по нажатию ругается» — демоушен снимает противоречие; primary «загорается» как награда и берёт роль индикатора «всё решено». AlertDialog-предохранитель остаётся. |
| Граница раздела — по равенству **эффективных путей** (полный массив), не `breadcrumb[0]` и не последний элемент | Имена листовых уровней не уникальны (то самое открытие, из-за которого крошка карточки — полная цепочка): два соседних подраздела «Материалы» под разными родителями при сравнении последнего элемента слились бы ровно там, где граница нужнее всего. |
| Предикат «открывашки» — структурный, по крошке следующей строки: строка X — открывашка ⟺ `next.breadcrumb === X.breadcrumb + [X.source_name]` | Статус excluded — НЕ детектор заголовка: заголовки без орг-токенов («Пожаротушение») классифицируются WORK, матчатся и стоят в полосе обычными строками ([classification.py](../../../backend/app/domain/classification.py) каскад + [estimate_matching_service.py](../../../backend/app/services/estimate_matching_service.py) `_classify_nodes`), а excluded бывает орг-листом без детей. Структурный предикат следует из конструкции крошки (дети X получают путь X + его имя), считается на фронте из имеющихся данных. **Равенства достаточно, prefix-сравнение не нужно:** крошка строится nearest-persisted-резолвом (`resolve_ancestor_indices` — непersистированные уровни в цепочке не появляются по построению, пропущенные выпадают), поэтому у первого персистированного потомка X крошка равна `X.breadcrumb + [X.name]` ТОЧНО, а не «начинается с»; персистированный промежуточный уровень сам встал бы между X и потомком в порядке документа. Равенство покрывает и пропущенные уровни, и вложенные открывашки — не «улучшать» до prefix-логики. **Семантика границы не зависит от `MatchStatus`; excluded сохраняет все текущие контракты** (не эмбедится, серверный guard PATCH, вне очереди и прогресса, приглушение) — статус остаётся в полосе только приглушением. |
| Разделитель перед открывашкой подавляется (самообъявление) | Подпись разделителя дублировала бы следующую же строку — заголовок объявляет себя сам. Разделитель незаменим там, где строки-заголовка между соседями НЕТ — этот класс данных реален: некодированные строки не персистятся узлами ([estimate_parser.py](../../../backend/app/services/estimate_parser.py): пустой/нечисловой «№ раздела» → `EstimatePosition`, не узел). |
| Строка-открывашка в полосе стилизуется как заголовок (вес/тон — на реализации) | Вторая половина правила самообъявления: разделитель глушится ИМЕННО потому, что заголовок объявляет себя сам, — обычной приглушённой строке объявлять себя нечем. Бонус: стиль работает и на краю окна ±2, где разделитель над открывашкой отрезан слайсом и подпись невозможна в принципе. С приглушением excluded композируется без конфликта: `opacity-60` сигналит «не решается в ревью», вес — структуру; оси разные. Парный тест (§5) держит обе половины правила вместе. |
| Подпись разделителя — имя-only («Раздел — Пожаротушение»); код раздела сознательно за скоупом | `breadcrumb` несёт только имена; `section_code` — код самой строки, не её раздела. Расширять контракт payload кодами предков ради подписи — несоразмерная цена. |
| Активная строка полосы: маркер «вы здесь» вместо `statusLabel` | «Требует проверки» у строки, которую оператор решает прямо сейчас, — дубль контекста. |
| Мульти-границы в окне ±2 — только тест, не код | Вычисление границы уже пер-парное (`win.map`, сравнение с предыдущей строкой) — две границы в окне отрисуются без правок. Нет лишь тест-кейса; существующий тест использует `getByTestId`, который на двух совпадениях падает, — мульти-тест пишется через `getAllByTestId`. |

## 3. PR-1 — косметика (поведение не меняется)

1. **Контейнер зоны решения** (`ReviewScreen`): обёртка `mx-auto w-full max-w-*`
   вокруг карточки (полоса переезжает внутрь, п.2). Грид, тулбар, терминальные
   экраны не трогаются. Значение `max-w` подбирается на живом экране
   (ориентир ~1100px; как `min-w` грида в этапе 3).
2. **Слот полосы** (`ReviewCard` + `ReviewScreen`): проп
   `contextStrip?: ReactNode`, рендер между блоком работы (код + имя) и блоком
   рекомендации/кандидатов. `ReviewScreen` передаёт готовый `<ContextStrip …/>`.
   Итоговый порядок в карточке: крошка сметы → строка работы → полоса окружения →
   рекомендация → кандидаты → поиск → «без пары» → легенда.
3. **Строка кандидата**: крошка перемещается к имени (`имя · крошка`, крошка
   вторичным стилем), `score` остаётся один у правого края. Синтетическая
   рекомендация — тем же шаблоном. Усечение крошки по **ширине**: крошка
   теперь делит строку с именем, длинный уровень (юр.название ВИС) не должен
   распирать строку — CSS-`truncate` по крошке, имя не жертвуется; полная
   цепочка в `title` уже есть из `CrumbTrail` (усечение по числу уровней —
   средний эллипсис — там же с этапа 2; ширинное появляется впервые).
4. **Демоушен «Завершить»** (`ReviewScreen`): `variant="outline"` при
   `pending > 0`, дефолтный primary при `pending === 0`. Ветвление диалога
   не меняется.
5. **Маркер активной строки полосы** (`ContextStrip`): для
   `row_number === activeRowNumber` правая часть — маркер (стрелка/точка,
   финальный вид на реализации), не `statusLabel`.

## 4. PR-2 — семантика границы раздела в полосе

Вся логика — в `ContextStrip`, работает на упорядоченном полном списке
(`ordered` уже есть в компоненте; предикату открывашки нужна следующая строка
в порядке документа, не окна). `topSection` удаляется.

Правила (в порядке применения, для каждой соседней пары окна):

1. **Эффективный путь** строки: `breadcrumb + [source_name]`, если строка —
   открывашка (см. предикат в §2), иначе `breadcrumb`.
2. Эффективные пути соседей **равны** → границы нет.
3. Граница есть, но **следующая строка — открывашка** своего раздела →
   разделитель подавлен (заголовок объявляет себя сам; покрывает и орг-,
   и WORK-заголовки). Строка при этом стилизуется как заголовок (§2) —
   подавление без стилизации оставило бы границу визуально неотбитой.
   Стилизация — по предикату, безусловно к положению в окне.
4. Иначе — **разделитель с подписью**: «Раздел — {последний элемент нового
   эффективного пути}» (имя-only), служебной плотностью (стиль текущего
   `section-boundary` + текст).

Краевые случаи (фиксируются тестами):

- последняя строка списка — не открывашка (следующей нет);
- открывашка склеена со своими детьми (границы между ними нет), граница
  встаёт над ней;
- вложенные открывашки сходятся (эффективный путь подраздела равен пути
  его работ);
- две границы в одном окне ±2 (строка в конце короткого подраздела) —
  оба разделителя отрисованы;
- excluded-строка в окне не влияет на вычисление границ (страж: границы
  считаются одинаково при любом статусе строк).

Деградация мягкая: при битых крошках (аномалии `parent_missing`/дубли кодов)
предикат открывашки просто не срабатывает — разделитель остаётся, дубль
подписи хуже пропавшей границы не бывает.

Известные края (зафиксированы, чтобы не были сюрпризом гейта):

- **заголовок без персистированных потомков** (все его позиции некодированные,
  в узлы не попали) неотличим от обычной строки — открывашку в нём не выдаёт
  ничто в данных. Граница над ним получает разделитель с подписью
  *родительского* раздела, а строкой ниже заголовок объявляет себя сам —
  лёгкий дубль со смещённой подписью. Безвредно и неустранимо из имеющихся
  данных; не чинить;
- **«путь укоротился»** (граница вверх по дереву — например, перед excluded
  орг-листом без детей): подпись именем родительского раздела нового пути
  семантически корректна, но на живом гейте взглянуть глазом.

## 5. Тесты и верификация

**vitest, PR-1:**

- `ReviewCard`: слот рендерится между строкой работы и кандидатами (порядок
  в DOM); без пропа — карточка как раньше;
- `ReviewCard`: крошка кандидата в одном контейнере с именем, score — у края;
- `ReviewScreen`: «Завершить» outline при `pending > 0`, primary при `0`;
- `ContextStrip`: у активной строки — маркер, не `statusLabel`;
- актуализация существующих тестов, задевающих DOM-порядок карточки/полосы
  (`ReviewScreen.test.tsx` рендерит полосу отдельно — переедет в слот).

**vitest, PR-2 (`ContextStrip.test.tsx`):**

- одноимённые листовые разделы под разными родителями РАЗДЕЛЯЮТСЯ границей
  (кейс, ради которого полный путь);
- два подраздела под одним верхнеуровневым разделом разделяются (кейс,
  на котором `breadcrumb[0]` молчал);
- парный тест самообъявления: разделитель перед открывашкой подавлен ∧
  открывашка несёт заголовочный стиль — и для excluded-, и для WORK-заголовка
  (обе половины правила в одном тесте: рефакторинг не унесёт одну без другой);
- открывашка на краю окна (разделитель отрезан слайсом) всё равно
  стилизована;
- разделитель с подписью там, где строки-заголовка между соседями нет;
- две границы в окне — `getAllByTestId("section-boundary")` длины 2;
- страж независимости от статуса (см. §4).

**Живой гейт:**

- PR-1: очередь на широком мониторе до/после (одна зрительная колонка);
  демоушен «Завершить» на смете с нерешёнными строками и после решения всех;
  карточка на ~1280px — и `max-w`, и шаблон «имя · крошка» на длинных
  крошках ВИС (первое место, где работает ширинное усечение крошки кандидата);
- PR-2: смета 16 — место с некодированным заголовком между разделами
  (единственный класс данных, где разделитель работает в одиночку, без
  подстраховки строкой-заголовком) и место с WORK-заголовком (подавление
  самообъявления, а не дубль подписи).

## 6. Вне скоупа (осознанно)

- Код раздела в подписи разделителя (расширение контракта payload кодами
  предков) — зафиксировано решением §2.
- Сокращение кандидатов до трёх, «Без пары» в ряд с поиском — упрощения
  макета; второе ждёт телеметрии.
- Механика окна ±2 и его размер, виртуализация полосы — не меняются
  (спека этапа 2 §5).
- Контракты excluded (классификация, guard PATCH, очередь, прогресс) —
  не трогаются нигде.

## 7. Риски

- **Слот меняет DOM-структуру карточки** — тесты с позиционными селекторами
  могут поплыть; закрывается актуализацией в PR-1 (п.4 списка тестов).
- **Предикат открывашки полагается на побайтовое равенство имён** в крошке
  и `source_name`. Обе строки происходят из одного `_clean_name` парсера
  (единая нормализация пробелов) — расхождение возможно только при изменении
  деривации крошки на бэке; страховка — мягкая деградация (§4) и живой гейт
  на смете 16.
- **`max-w` подбирается вживую** — риск «подобрали под один монитор»;
  смягчение: гейт на двух ширинах (широкий монитор + ~1280px).
