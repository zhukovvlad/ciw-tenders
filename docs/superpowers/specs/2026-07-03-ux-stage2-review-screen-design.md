# Этап 2 UX-роадмапа: экран ревью под тысячи строк

**Дата:** 2026-07-03
**Родитель:** [2026-07-02-ux-roadmap-design.md](2026-07-02-ux-roadmap-design.md) §4 — все решения §4
действуют; этот документ уточняет их до уровня реализации и фиксирует решения брейнсторма.
**Макет:** обсуждён в визуальном компаньоне 2026-07-03 (очередь/таблица, карточка с крошками обеих
сторон, error-строка, пустая очередь); направление одобрено.

## 1. Решения брейнсторма (поверх §4 роадмапа)

| Решение | Обоснование |
|---|---|
| Одна спека, **два плана / два PR** | PR-A (бэк-контракт + контракт excluded) мал и самоценен: чинит реальный дефект (клавиатура встаёт на нерешаемые строки). PR-B (карточка + грид + терминальные экраны) строится на чистом контракте. Меньше риск гигантского ревью. |
| Дефолт при открытии сметы в ревью — **режим «Очередь»** | Оператор в работе с первого экрана (карточка на первой нерешённой). Если спорных нет — терминальный экран «все спорные решены». |
| Режим в URL: **`?view=grid`** — таблица; без параметра — дефолт | Дефолт: очередь для открытой сметы, итоговый экран для завершённой. Шареабельная ссылка на таблицу, F5 держит режим, back работает; фаза остаётся серверной (этап 1), режим — клиентский выбор, но адресуемый. |
| Архитектура фронта — **слоистая** | `reviewState`-редьюсер НЕ меняется (решения = зеркало сервера: гидратация из `review_status`, оптимистичные апдейты, PATCH-перезапись). Навигация — новый сессионный слой `useReviewQueue` (порядок, skip-в-хвост, undo-стек, активная строка). Карточка и грид — презентационные компоненты над обоими. |
| **Крошки с обеих сторон** | Строка сметы: `breadcrumb` в карточке (предки решаемой строки). Кандидаты/рекомендация/результаты поиска: крошка из дерева справочника — одноимённые статьи («Прочее» в нескольких разделах) различимы только родителем. |
| Breadcrumb сметы — **позиционный пересчёт, не разбор `embedding_input`** | Роадмап предлагал деривацию из `embedding_input` и помечал её хрупкой (в названиях есть точки). Вместо парсинга бэк на чтении пересчитывает цепочки предков тем же алгоритмом, что парсер: `resolve_ancestor_indices` по `depth` в порядке `source_index` над строками сметы. Результат байт-в-байт равен парсерному; формат `embedding_input` остаётся внутренним; запасная колонка не нужна. |
| Breadcrumb кандидата — **дерево `parent_id` справочника** | Надёжный источник (честное дерево `template_articles.parent_id`). Кандидат с потерянным `id` (статья удалена из справочника) — крошка не показывается, graceful fallback. |

## 2. PR-A — бэк-контракт и контракт excluded-узлов

### 2a. Бэкенд: payload строки

`EstimateRowOut` дополняется:

- `source_index: int` — порядок исходного документа (полоса контекста, PR-B);
- `match_error: str | null` — текст ошибки для `error`-строк (карточка, PR-B);
- `breadcrumb: list[str]` — имена предков строки **без самого узла** (фронт сам ставит разделитель).
  Деривация — позиционный пересчёт (см. §1). Страж-тест: для каждой строки
  `". ".join(breadcrumb + [name]) == embedding_input` (плюс ручная сверка на живой dev-БД).

`MatchCandidateOut` (кандидаты строки) и ответ `GET /articles/search` дополняются
`breadcrumb: list[str]` — имена предков статьи по `parent_id` (без самой статьи); для кандидата
без `id` — пустой список. Дерево справочника мелкое (2–3 уровня, 362 статьи) — цепочки собираются
одним проходом по загруженной карте `id → (name, parent_id)`, без рекурсивных запросов.

### 2b. Фронтенд: контракт excluded (лечится на ТЕКУЩЕЙ таблице, до карточки)

- `MatchStatus` расширяется до полного множества статусов бэка: `+ "excluded" | "pending"`.
  Чип статуса — exhaustive switch (новый статус бэка ловится компиляцией).
- Очередь хоткеев в текущем `ReviewScreen`: `rows.filter((r) => r.status !== "confident")` →
  `rows.filter(requiresDecision)` — excluded/pending/фонд-хиты выходят из клавиатурной навигации
  (зеркально счётчикам, починенным фиксом `requiresDecision` в PR #20).
- Excluded/pending-строки в таблице: приглушённые (muted), лейблы «Контекст» / «В обработке»,
  не раскрываются в аккордеон.
- Типы/DTO фронта: `MatchRow` получает `sourceIndex`, `breadcrumb`, `matchError`;
  `Candidate` — `breadcrumb`. `rowFromDto` мапит новые поля.

Гасит пункты (4)–(5) TECH_DEBT «Этап 1 UX-роадмапа: полировка из ревью».

## 3. PR-B — карточка, грид, терминальные состояния

### 3a. Слой навигации `useReviewQueue`

Сессионный (in-memory) hook поверх нетронутого `reviewState`:

- **Порядок** — спорные строки (`requiresDecision`) по `source_index` возрастанию.
- **Активная строка** — первая нерешённая в порядке очереди, либо явный выбор
  (клик из грида, `←`).
- **`N` (пропустить)** — строка в хвост сессионного порядка; после F5 порядок исходный.
- **Undo-стек `←`** — каждый закоммиченный ответ пушит номер строки; `←` снимает вершину и
  открывает ту строку с её решением (перерешение = существующий PATCH-перезапись). После
  перезагрузки стек пуст — `←` неактивна; переоткрыть решённую можно кликом из грида.
- **Ошибка PATCH** — строка возвращается в **голову** очереди + toast с именем строки
  (колбэк из `EstimatePage.handleReview.catch`; сейчас откат молча уходит в общий пул).
- Очередь карточки — всегда все нерешённые спорные сметы; фильтры/чипы действуют только в гриде.

### 3b. Карточка решения (единственная поверхность)

Собирается из shadcn-примитивов (Card/Command/Badge/Button); содержимое сверху вниз:

1. Крошка сметы (`breadcrumb`, приглушённая).
2. Работа из сметы — полный текст (без клампа), код.
3. Рекомендация — «Рекомендация AI» / «Из фонда» (гейт синтетической рекомендации переезжает из
   `ReviewRow` без изменений) + крошка справочника + score + `Enter`.
4. Кандидаты `1/2/3` — код, имя, крошка справочника, score.
5. Поиск по справочнику (существующий серверный, shadcn `Command`) — результаты с крошками.
6. «Оставить без пары» (`0`).
7. Постоянная легенда клавиш: `1–3`, `0`, `Enter`, `N`, `←`.

**Error-строки** (`partial_error`-сметы): вместо рекомендации/кандидатов — текст `match_error`;
действия — поиск и «без пары»; `Enter`/`1–3` неактивны. «Повторить обработку» — вне скоупа.

**`no_match`-строки**: рекомендации нет (`matched_*` пусты) → `Enter` неактивен; кандидаты, если
вектор что-то вернул, доступны под `1–3`; иначе — поиск и `0`. Общее правило карточки: клавиша
активна ⇔ соответствующий элемент отрисован.

**Полоса контекста** (под карточкой, видима по умолчанию): ±2 соседних узла по `source_index`
среди **всех** строк (включая excluded — приглушённые). Формат «код · название → статья/статус»;
граница верхнеуровневого раздела — видимый разделитель. Листовые позиции без номера не персистятся
и в полосу не входят (вне скоупа, роадмап §4).

**Клавиатура**: расширяем существующий `useReviewKeyboard` клавишами `0` и `←`; активен только в
режиме «Очередь»; глушится, когда фокус в инпуте поиска.

### 3c. Read-only грид (`?view=grid`)

- `@tanstack/react-virtual` (новая зависимость), div-разметка в визуальном языке shadcn Table и
  токенах MR DS; фиксированная высота строки, текст работы клампится до 2 строк (полный — в карточке).
- Sticky-шапка; чипы/фильтры/счётчики — как сейчас.
- Клик по строке (включая confident/фонд) → режим «Очередь» с этой строкой активной;
  «к таблице» возвращает на позицию скролла (`scrollToIndex` по последней позиции грида; если в
  очередь вошли не из грида — скролл к активной строке). Excluded/pending — некликабельные.
- Шапка экрана (оба режима): имя файла, «спорных решено X из Y», переключатель «Очередь / Таблица»,
  «Выгрузить Excel», «Завершить» (с существующим диалогом при остатке нерешённых).
- `ReviewRow` и аккордеон удаляются; их тесты переписываются под карточку/грид.

### 3d. Терминальные состояния и завершённая смета

- Пустая очередь → экран «Все спорные строки решены»: сводка (решено/сопоставлено/без пары),
  CTA «Завершить проверку», ссылка «Посмотреть таблицу».
- Завершённая смета (`completed_at`): дефолт — итоговый экран (этап 1, без изменений);
  `?view=grid` — тот же грид в read-only: клик в карточку выключен, экспорт доступен.
- Экспорт не меняет фазу (уже так с этапа 1).

## 4. Тестирование и гейты

- **PR-A бэк:** юниты на breadcrumb-деривацию (вложенность, дубли кодов — позиционный резолв,
  корневые узлы → `[]`), страж `". ".join(breadcrumb + [name]) == embedding_input` по всем строкам
  фикстур; крошки кандидатов (обычный, без `id`); `source_index`/`match_error` в DTO.
  Ручная сверка breadcrumb на живой dev-БД (смета 16 — 294 строки с дублями и excluded).
- **PR-A фронт:** exhaustive-чип (компиляция), очередь от `requiresDecision`, приглушение.
- **PR-B:** юниты `useReviewQueue` (порядок, skip-в-хвост, undo, голова-очереди-при-ошибке PATCH,
  пустая очередь); карточка (рекомендация/кандидаты/поиск/без пары, error-вариант, крошки);
  клавиатура (`0`, `←`, глушение в поиске); грид — smoke на окно виртуализации и `scrollToIndex`;
  терминальный экран; read-only-режим.
- **Обязательные ручные гейты (оба PR):** браузерный прогон на живых dev-серверах —
  PR-A: смета с excluded-строками (клавиатура не встаёт на них, лейблы честные);
  PR-B: полный поток карточки (решение хоткеями, skip, undo, ошибка PATCH → голова очереди,
  переключение режимов, F5 в каждом режиме, завершение из обоих режимов, read-only).

## 5. Вне скоупа (осознанно)

- Повторная обработка error-строки; возврат excluded-строки в матчинг.
- Ед. изм. и количество в карточке (парсер их не читает — роадмап, таблица решений).
- Виртуализация полосы контекста (±2 строки — константный размер).
- Запоминание выбранного режима между сессиями (дефолт детерминирован; состояние — только URL).
- Светлая тема, i18n (этапы 3–4).

## 6. Риски

| Риск | Смягчение |
|---|---|
| Позиционный пересчёт breadcrumb разойдётся с `embedding_input` на старых сметах (парсер эволюционировал) | Страж-тест сравнением + ручная сверка на dev-БД; при расхождении — breadcrumb из пересчёта считается истиной для UI (это отображение, не эмбеддинг), расхождение логируется. |
| Фиксированная высота строки грида ломается на экстремальных названиях | Кламп 2 строки + полный текст в карточке; высота задаётся токеном, меряется на реальной смете 16 в ручном гейте. |
| Хоткеи конфликтуют с фокусом поиска/диалогов | Единая точка глушения в `useReviewKeyboard` (фокус в инпуте / открыт диалог); пин-тесты. |
| Два PR — промежуточное состояние между A и B | PR-A самоценен (контракт+лечение excluded на текущей таблице); карточки в нём нет, UX не хуже текущего ни в одной точке. |
