# UX/UI-роадмап: фундамент → ревью → консистентность → локализация

**Дата:** 2026-07-02
**Статус:** дизайн согласован, ждёт ревью спеки
**Скоуп:** четыре последовательных этапа улучшения UX/UI; каждый этап — отдельная спека+план+PR.

## 1. Контекст и диагноз

Аудит фронтенда (2026-07-02) показал: дизайн-система (MR DS) и механика ревью
(очередь, шорткаты, оптимистичный UI) — сильные, но интерфейс не выдерживает
целевых объёмов и не имеет структуры приложения.

Целевые параметры (подтверждены):
- **Аудитория:** команда смётчиков-операторов (десктоп) + демо руководству.
- **Масштаб смет:** тысячи строк СМР в одной смете.
- **Справочник:** 362 статьи сейчас (замер по БД 2026-07-02); курируемый
  шаблон, потолок ~единицы тысяч. Список смет растёт линейно от работы операторов.

Ключевые проблемы по убыванию тяжести:
1. Ревью рендерит все строки одной таблицей — на тысячах строк парадигма не работает.
2. Нет роутера: нельзя дать ссылку на смету, «назад» не работает, состояние — в sessionStorage.
3. Эргономика ревью невидима: шорткаты `Enter`/`N` нигде не показаны, нет undo.
4. Визуальная неконсистентность: смесь shadcn `Table` и сырых `<table>`, ошибки то инлайн, то toast, слабая адаптивность.
5. Все тексты захардкожены по-русски — часть команды туркоязычна.

## 2. Ключевые решения (и почему)

| Решение | Обоснование |
|---|---|
| Порядок: фундамент → ревью → лоск → i18n | Каждый этап строится на устойчивом основании; полировка и извлечение строк из экранов, которые перепишутся, — двойная работа. |
| Завершение сметы — серверное поле `completed_at`, не расширение enum статусов | Enum описывает пайплайн обработки, а не жизненный цикл; ссылка на закрытую смету не должна открывать редактирование. |
| Навигационного блокера и `beforeunload` НЕ будет | Каждое решение сразу коммитится `PATCH`-ем, `initReview` гидратирует прогресс из `review_status` — при уходе не теряется ничего, кроме позиции в очереди. Вместо guard'а — видимый прогресс `reviewed/total` в списке смет. |
| sessionStorage-кэш ревью удаляется целиком | Сервер — единственный источник истины (`GET` + `PATCH`-ответы); с шареабельными ссылками кэш становится источником рассинхрона. |
| Виртуализация ревью — в этапе 2, не в 1 | Этап 2 меняет разметку строк; виртуализировать старую разметку и перемерять высоты на новой — двойная работа. |
| Справочнику серверная пагинация НЕ нужна | 362 статьи, курируемый шаблон. Грузим целиком + клиентский фильтр (уже написан). Серверный поиск остаётся — нужен панели ревью. |
| Одна поверхность решения (карточка), таблица read-only | Две поверхности (карточка + аккордеон) = двойные тесты, двойная клавиатурная обвязка, дрейф. Read-only грид даёт строки фиксированной высоты → виртуализация без dynamic measurement (самая капризная часть `react-virtual` выпадает). Editable-confident-rows получается бесплатно: клик по confident-строке открывает ту же карточку. |
| Перезапись решения — без изменений бэка | Проверено: `EstimateReviewService.apply` отклоняет только `pending`-строки; повторный `PATCH` перезаписывает `review_status`/`final_*`, AI-снимок (`matched_*`/candidates) не трогается. |
| i18n — отдельный этап 4, глубина «UI + коды ошибок» | Извлечение строк — после стабилизации экранов. Бэк переходит на коды ошибок (это правильная архитектура независимо от i18n). Данные (наименования работ, статьи) не переводятся. |
| Крошка раздела в карточке — из `embedding_input` | Полная цепочка предков уже хранится в `estimate_rows.embedding_input` (позиционный резолв, устойчивый к дублям кодов — клиентская реконструкция по `parent_code` дала бы расхождение). Работа = добавить поле в `EstimateRowOut`. |
| Ед. изм. и количество в карточке — отложено | Парсер их не читает вовсе (только №/Наименование/Вид раздела); добавление = парсер + миграция + бэкфилл старых смет. Отдельная задача, если операторы попросят. |
| Права «владелец и админ» — существующая модель | Проверено: `estimates.user_id` + `list_for_owner`/`get(requester_id, is_admin)` уже реализуют ownership; новой модели данных не требуется. |

## 3. Этап 1 — Фундамент: роутер и жизненный цикл сметы

**Фронтенд:**
- react-router (library mode). Маршруты: `/estimates` (загрузка + список),
  `/estimates/:id` (фаза определяется статусом с бэка), `/articles`.
  Логин остаётся гейтом поверх всего (SPA закрыта целиком, редиректить некуда).
- Маппинг статус → экран: `pending`/`running` → прогресс; `ready`/`partial_error`
  без `completed_at` → ревью; с `completed_at` → **итоговый экран** (сводка,
  экспорт, тумблер фонда) с переходом «Просмотреть строки» → read-only грид
  (см. §4.2d — там детали read-only-режима); `blocked` — некликабелен в списке.
- Табы `AppShell` → `NavLink`; «назад» браузера работает; бренд в шапке кликабелен → `/estimates`
  (перенесено из этапа 3 — тривиально при вводе роутера).
- Удаление sessionStorage-кэша ревью (`lib/session.ts` review-часть) и `beforeunload`-guard.
  `/estimates/:id` всегда делает `GET`. Потеря позиции в очереди при F5 — приемлема
  (очередь пересчитывается как «первая нерешённая»).
- `EstimateList`: колонка прогресса «проверено X из Y» из данных списка.

**Бэкенд:**
- Поле `estimates.completed_at` (nullable timestamp) + миграция. Эндпоинт
  завершения/возобновления (выставить/снять). Права — по существующей модели доступа
  (владелец и админ).
- Список смет: пагинация (`limit/offset`) + `reviewed_count`/`total_reviewable` в элементах.

**Чего в этапе нет:** изменений разметки/механики ревью, виртуализации, визуальных правок.

## 4. Этап 2 — Экран ревью под тысячи строк

**2a. Карточка решения — единственная поверхность.**
- Содержимое: крошка раздела, работа из сметы (полный текст), кнопка
  «Рекомендация AI»/«Из фонда», кандидаты, поиск по справочнику (существующий
  серверный), «без пары».
- Клавиатура: `1/2/3` — кандидат, `0` — без пары, `Enter` — подтвердить
  рекомендацию, `N` — пропустить (строка остаётся в хвосте очереди), `←` —
  к предыдущей решённой (переоткрытие; бэк уже допускает перезапись).
- Семантика `←`: стек истории решений **текущей сессии** (in-memory). После
  перезагрузки стек пуст — кнопка/клавиша неактивны; переоткрыть решённую
  строку всё равно можно кликом из грида.
- Очередь карточки — всегда **все** нерешённые спорные строки сметы; фильтры и
  чипы действуют только в гриде (изменение относительно текущего поведения,
  где queue строится из отфильтрованного набора).
- Постоянная легенда клавиш в карточке.
- Полоса контекста: ±2 **соседних узла по `source_index`** (порядок исходного
  документа, включая не-матчируемые заголовки — все кодированные узлы уже
  персистятся и приходят на фронт), приглушённые, read-only, формат «название →
  присвоенная статья/статус». Граница раздела в полосе визуально видима.
  Листовые позиции без номера не персистятся и в полосу не входят (вне скоупа).
  По умолчанию полоса видимая. Обоснование: строки смет идут семантическими
  кластерами — соседи различают омонимичные работы (тот же аргумент, что привёл
  к breadcrumb в эмбеддинге), плюс оператор видит несогласованность с соседями
  в момент решения.
- Строки со статусом `error` (в `partial_error`-сметах): попадают в очередь;
  карточка показывает текст `match_error` вместо кандидатов; доступные действия —
  поиск по справочнику и «без пары». «Повторить обработку строки» — вне скоупа.
- Ошибка коммита `PATCH`: строка возвращается в **голову** очереди + toast с
  именем строки — оператор разбирается с проблемой, пока контекст ещё в голове
  (сейчас откат молча уходит в общий пул).

**2b. Read-only грид — обзорный режим.**
- Виртуализация (`@tanstack/react-virtual`), div-grid вместо `<table>`,
  фиксированная высота строк: текст работ клампится до 2 строк (полный — в карточке).
- Sticky-шапка, фильтры/статус-чипы/счётчики — как сейчас.
- Клик по строке (любой, включая confident) → карточка на этой строке.
  «← к таблице» возвращает на ту же позицию скролла (`scrollToIndex`).
- Аккордеон и вторые `<tr>` удаляются; тесты `ReviewRow` переписываются под карточку.

**2c. Терминальные состояния.**
- Пустая очередь → экран «все спорные решены»: сводка + CTA «Завершить».
- «Завершить» доступна и из грида; при остатке нерешённых — диалог
  «осталось N спорных, завершить всё равно?».
- Экспорт `.xlsx` больше не меняет фазу — промежуточная выгрузка доступна всегда.

**2d. Завершённая смета (`completed_at`).**
- По ссылке открывается итоговый экран (маппинг — §3); «Просмотреть строки» ведёт
  в read-only грид: без перехода в карточку, экспорт доступен.
- Кнопка «Возобновить проверку» (снимает `completed_at`; владелец/админ).
- Тумблер «в фонд решений» остаётся на итоговом экране.

**2e. Бэкенд-часть этапа.**
- `EstimateRowOut` дополняется: `breadcrumb` (из хранимого `embedding_input`) —
  для крошки раздела в карточке; `match_error` — для карточки error-строк;
  `source_index` — для полосы контекста (порядок исходного документа).
- Единица измерения и количество — НЕ входят (не парсятся вовсе; см. таблицу решений).

## 5. Этап 3 — Консистентность и демо-лоск

- **Единый табличный язык:** `EstimateList`, `ArticleTable`, `StructureNotice`,
  review-грид — один компонентный стиль (shadcn-базис + токены MR DS), без сырых `<table>`.
- **Политика фидбека:** инлайн (`FormMessage`) — валидация форм; toast — исходы
  асинхронных действий. Логин → инлайн-ошибки. Тумблер фонда: disabled с
  пояснением при 0 подтверждённых вместо «отщёлкивания» с toast.
- **Адаптивный минимум:** десктоп-first, цель «не ломается»: `overflow-x` для
  широких таблиц, шапка сворачивается на узких окнах (пол-экрана рядом с Excel — рабочий кейс).
- **Мелочи:** единый хелпер плюрализации (уйдёт в i18n-механику этапа 4);
  персист аномалий структуры на бэке + возврат в `GET /estimates/{id}`
  (сейчас `StructureNotice` теряется при перезагрузке).

## 6. Этап 4 — Локализация (русский + турецкий)

Глубина: **UI-хром + коды ошибок** (подтверждено).

- **Фронтенд:** react-i18next; извлечение всех строк в словари `ru`/`tr`;
  плюрализация через i18next (заменяет ручной `pluralizeZamechanie` и хелпер из
  этапа 3); переключатель языка в меню пользователя, выбор персистится.
  Форматирование дат/чисел — через выбранную локаль (сейчас
  `Intl.DateTimeFormat("ru-RU")` захардкожен в `EstimateList`).
- **Бэкенд:** пользовательские ошибки переходят на машинные коды
  (`estimate_not_found`, `row_not_matched`, …) в теле ответа; фронт маппит
  код → локализованный текст. Русские `detail`-тексты остаются как fallback.
- **Не переводится:** данные (наименования работ из смет, статьи справочника,
  содержимое экспорта) — это контент на языке документов. Сюда же — заголовки
  и статусы, которые приложение пишет в экспортный .xlsx («Статья СМР»):
  формально это UI-хром, но документ живёт в русскоязычном документообороте
  и должен быть одинаковым независимо от локали оператора.
- **Качество перевода:** черновик — LLM, финальная вычитка — туркоязычные
  коллеги (у сметной терминологии устоявшийся профессиональный словарь:
  keşif, poz, metraj).

## 7. Вне скоупа (осознанно)

- Светлая тема — тёмная единственная по решению дизайн-системы.
- Редизайн токенов MR DS — система хороша, проблема в неровном применении (этап 3 её выравнивает).
- Мобильная версия — только «не ломается» (этап 3).
- Виртуализация `ArticleTable` и пагинация справочника — не нужны на 362 статьях;
  пересмотреть, если справочник вырастет на порядок.

## 8. Риски

- **Dynamic measurement всё же понадобится**, если кламп в 2 строки окажется
  нечитаемым для операторов — тогда грид переходит на measured-высоты
  (умеренная сложность, но уже без аккордеона).
- **Гонки при совместной работе** двух операторов над одной сметой этап 1 решает
  только частично (сервер побеждает кэш); последний `PATCH` выигрывает без
  предупреждения. Осознанно принято: одновременное ревью одной сметы — не
  целевой сценарий. Если станет им — оптимистичные блокировки отдельной задачей.
- **Терминология турецкого перевода** — риск смягчается вычиткой носителями.
