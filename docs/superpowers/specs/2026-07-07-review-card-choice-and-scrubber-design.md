# Дизайн: блок «Ваш выбор» + скраббер-навигация по окружению

**Дата:** 2026-07-07
**Область:** фронтенд, экран ревью сметы (`pages/estimate/*`, `lib/useReviewQueue.ts`)
**Статус:** согласован, готов к плану реализации

## Проблема

Две связанные шероховатости на карточке ревью, обе всплыли при клике по решённой
строке из таблицы (грида):

1. **Решение оператора невидимо.** Грид показывает финальный выбор
   (`final_code`/`final_name`), а карточка очереди ведёт с исходной рекомендацией
   системы (`matched_code`/`matched_name`). Для переопределённой (override) строки
   это разные статьи: таблица показывает `4.2 Надземная часть`, а карточка —
   `4.2.4 Устройство вертикальных…` (рекомендация из фонда). Выбор оператора
   виден только приглушённой подсветкой кандидата (а если он был сделан через
   поиск и не входит в кандидаты — не виден нигде). Самое важное решение оператора
   должно быть самым заметным элементом карточки.

2. **Полоса окружения — только справка.** `ContextStrip` показывает ±2 соседних
   строки, но по ним нельзя перейти. Оператор видит соседа, требующего внимания,
   и не может кликнуть, чтобы к нему перейти.

## Фича 1 — блок «Ваш выбор»

Презентационное изменение в [ReviewCard.tsx](../../../frontend/src/pages/estimate/ReviewCard.tsx).
Логика ревью (`reviewState`, `useReviewQueue`) не трогается.

### Когда показывается

Блок рендерится, когда `decision.kind === "confirmed"` **и**
`decision.code !== row.matched_code`. То есть выбор оператора отличается от
исходной рекомендации системы: ручной override, выбор не-рекомендованного
кандидата, ИЛИ выбор из поиска на строке без рекомендации (`matched_code = null`).

Если оператор подтвердил саму рекомендацию (`decision.code === row.matched_code`) —
блок НЕ показывается: подсветка рекомендации и так верна, дублировать незачем.

`no_match` (reject) и `error` — блок не показывается (см. ниже).

### Что показывает

- Метка `★ review.yourChoice` («Ваш выбор»).
- `decision.code` + `decision.name`.
- Крошка статьи, источник в порядке приоритета:
  1. кандидат из `row.candidates`, чей `article_code === decision.code` → его `breadcrumb`;
  2. иначе `row.finalBreadcrumb`, но только при `decision.code === row.final_code`
     (гарантия свежести: PR-A гидратирует PATCH-ответ, поэтому `finalBreadcrumb`
     актуален даже для выбора из поиска в текущей сессии — но сверяем с `final_code`,
     чтобы не показать устаревшую крошку в переходном окне до синка);
  3. иначе крошка не показывается.
- Стиль — `border-primary` + фиолетовое свечение (`--ds-glow-violet`), как у
  выбранного кандидата.

### Расположение и демоушен рекомендации

Блок встаёт **между** `contextStrip` и блоком рекомендации/кандидатов. Секция
рекомендации уходит вниз под подпись `review.systemRecommendationLabel`
(«Рекомендация системы»). **При отсутствии рекомендации** (`matched_code = null`)
блок «Ваш выбор» показывается, а секция рекомендации не рендерится вовсе.

### Гашение Enter на решённых строках (осознанное решение)

`Enter` (`confirmArbiter`) подтверждает рекомендацию. На решённой-с-override
строке это перезаписало бы выбор оператора одним нажатием — а теперь рекомендация
стоит под блоком «Ваш выбор», и случайный `Enter` вероятнее.

**Правило:** `Enter` / `confirmArbiter` активен **только пока строка не решена**
(`decision.kind === "pending"`). На решённой строке рекомендация показывается
(кликом её можно вернуть), но **без бейджа `Enter`**, и клавиша инертна.

Обоснование:
- защищает подтверждённое решение оператора от перезаписи одним нажатием;
- сохраняет инвариант «клавиша ⇔ элемент» (нет бейджа `Enter` ⇒ нет клавиши);
- **не трогает основной поток**: решённые строки возникают только при ре-навигации
  (клик из грида/полосы), в линейном проходе активная строка всегда `pending`.

Реализация: `useReviewKeyboard`-гейт `canConfirm` дополняется условием
`decision.kind === "pending"`; в `ReviewCard` бейдж `Enter` и роль «клик = confirm
рекомендации» скрываются на решённой строке (клик по рекомендации остаётся как
явный ручной возврат к ней).

### i18n

Новые ключи в обоих файлах ([ru.json](../../../frontend/src/locales/ru.json),
[tr.json](../../../frontend/src/locales/tr.json); parity-тест требует полноты):
- `review.yourChoice` — RU «Ваш выбор», TR «Seçiminiz»;
- `review.systemRecommendationLabel` — RU «Рекомендация системы», TR «Sistem önerisi».

## Фича 2 — клик по строкам окружения (скраббер)

Поверхность: [ContextStrip.tsx](../../../frontend/src/pages/estimate/ContextStrip.tsx)
+ логика очереди в [useReviewQueue.ts](../../../frontend/src/lib/useReviewQueue.ts).

### Кликабельный набор

Кликабельны все строки, **кроме** `excluded`/`pending` (как в гриде):
`needs_review` / `no_match` / `error` / `confident` / `matched_fund`. Клик делает
строку активной немедленно. Клик по уже активной строке — no-op.

### Скраббер-модель (замена flow-переходов)

У очереди появляется понятие **текущей позиции** = `sourceIndex` активной строки.
После решения (confirm/pick/reject) или пропуска (skip) поток идёт к **следующей
нерешённой спорной строке после текущей позиции** по порядку документа
(`sourceIndex`); если дальше нет — оборачивается к самой ранней нерешённой; если
нерешённых нет — `QueueDone`. Никакого «возврата к исходной строке» — оператор
движется в одном направлении по смете, полоса лишь позволяет переставить точку,
откуда продолжать.

**Обратная совместимость (честная граница фичи):** при обычном линейном проходе
сверху вниз позиционная модель совпадает с текущим поведением — следующая
нерешённая всегда впереди текущей позиции. Меняется **только** сценарий с прыжком.

### Границы: что скраббер НЕ поглощает

Скраббер заменяет **только flow-переходы** (`origin.kind === "flow"`). Два других
origin сохраняются без изменений:

- **`origin=grid`** (пришёл из таблицы точечно поправить): `exitFor(origin=grid)`
  живёт — после решения возврат в грид (`switchToGrid`). Ссылка: спека этапа 2 §3a,
  с тестами. Скраббер этот выход не трогает.
- **`←` / undo** (`origin=undo`): сохраняется **возврат к прежней активной**
  (`returnTo`). Undo — это отступление, не навигация; скраббер его не поглощает.
  Ссылка: `useReviewQueue.undo` + существующие тесты.

### Совместимость с «ошибка PATCH → строка в голову» (обязательно)

Инвариант PR-B: при ошибке PATCH откатившаяся строка становится СЛЕДУЮЩЕЙ, чтобы
оператор разобрался, пока контекст в голове ([useReviewQueue.commitFailed](../../../frontend/src/lib/useReviewQueue.ts)).
В позиционной модели «головы» нет. Чтобы инвариант не умер молча:

**`commitFailed` принудительно ставит текущую позицию ПЕРЕД откатившейся строкой** —
тогда «следующая нерешённая после позиции» это и есть откатившаяся строка.
Инвариант сохранён без понятия головы. Требует теста.

### A11y и аффорданс кликабельности

- Кликабельные строки — настоящие `<button type="button">` (фокус, Enter/Space,
  видимый focus-ring). `excluded`/`pending` остаются неинтерактивными (`<div>`).
- Аффорданс — **словарь грида, НЕ рамка кандидата**: `hover:bg-muted/50`
  (или эквивалентный тинт) + `cursor-pointer`. В покое полоса остаётся утопленной
  справкой (`--ds-surface-sunken`), интерактивность проявляется только на hover —
  проблема «полоса читается как кандидаты» (этап 3.6) не возвращается.
- Отдельных горячих клавиш для навигации по полосе нет (клик/фокус+Enter).

### Эволюция роли поверхности 3.6 (решение уровня таблицы)

Этап 3.6 стоял на «залитая тихая панель = справка, обведённые строки = кнопки».
Фича 2 расширяет роль полосы: **«справка» → «справка + навигация»**. Это
осознанная эволюция, а не побочный эффект. Санкция воркеру:

- регресс-гвард «строки полосы не несут словаря кандидата»
  ([ContextStrip.test.tsx:302](../../../frontend/src/pages/estimate/ContextStrip.test.tsx#L302))
  запрещает словарь кандидата (`rounded`, `border-border`), а не интерактивность.
  Выбранный аффорданс (hover-тинт грида) его не нарушает — **гвард проходит без
  правок**. Если резет-классы `<button>` его случайно заденут — гвард можно
  поправить, но беречь его **намерение** (полоса ≠ кандидаты: без `rounded`/
  `border-border`/рамки кандидата), а не букву.

### Проброс колбэка

Навигация не имеет доступа к `useReviewQueue` из `ContextStrip`. Колбэк
`onNavigate(rowNumber)` пробрасывается `ReviewScreen → ReviewCard (проп рядом с
contextStrip) → ContextStrip`. В `ReviewScreen` он вызывает новый метод очереди
(навигация с `origin=flow`, позиция = `sourceIndex` строки). Сама навигация
**не пишется в undo-стек** (это не решение).

## Тесты

**ReviewCard** ([ReviewCard.test.tsx](../../../frontend/src/pages/estimate/ReviewCard.test.tsx)):
- блок «Ваш выбор» появляется при override и при выборе не-рекомендованного кандидата;
- блок появляется на решённой `no_match`-строке без рекомендации (выбор из поиска,
  `matched_code = null`), секция рекомендации при этом не рендерится;
- блок отсутствует при подтверждённой рекомендации, при `pending`, при `error`;
- крошка блока берётся из кандидата по коду / `finalBreadcrumb` / отсутствует;
- `Enter` подтверждает рекомендацию на `pending`-строке; на решённой строке
  бейдж `Enter` отсутствует и клавиша инертна.

**useReviewQueue** ([useReviewQueue.test.ts](../../../frontend/src/lib/useReviewQueue.test.ts)):
- навигация делает произвольную решаемую строку активной, origin=flow;
- после решения — «следующая нерешённая после позиции», обёртка к ранней, `QueueDone` в конце;
- линейный проход сверху вниз не изменился (пин обратной совместимости);
- ad-hoc строка (confident/фонд) из полосы: решается, поток продолжается от её позиции;
- навигация не трогает undo-стек;
- `commitFailed` ставит позицию перед откатившейся строкой → она следующая (пин PR-B);
- `origin=grid` после решения по-прежнему уходит в грид (пин §3a);
- `←`/undo по-прежнему возвращает к прежней активной (`returnTo`).

**ContextStrip** ([ContextStrip.test.tsx](../../../frontend/src/pages/estimate/ContextStrip.test.tsx)):
- клик по решаемой строке зовёт `onNavigate` с её `row_number`;
- `excluded`/`pending` не кликабельны (не `<button>`, `onNavigate` не зовётся);
- кликабельная строка несёт аффорданс грида (hover-тинт/cursor), но НЕ словарь
  кандидата (регресс-гвард роли сохранён по намерению).

## Вне области (YAGNI)

- Горячие клавиши для навигации по полосе.
- Блок «Ваш выбор» для `no_match`-reject без выбора статьи (там выбор = «без пары»,
  его несёт подсветка кнопки «Оставить без пары» — не меняем).
- Изменение серверного контракта / DTO — фичи чисто клиентские.
