# Этап 4 UX-роадмапа: локализация (русский + турецкий)

**Дата:** 2026-07-06
**Статус:** дизайн согласован, ждёт ревью спеки
**Родитель:** [2026-07-02-ux-roadmap-design.md](2026-07-02-ux-roadmap-design.md), §6
**Скоуп:** UI-хром фронтенда + машинные коды ошибок на бэкенде. Два PR.

## 1. Контекст

Аудитория: операторы-десктоп (русскоязычные и туркоязычные) + демо руководству.
Инвентаризация (2026-07-06):

- **Фронт:** i18n-зависимостей нет; ~23 tsx-файла с русскими литералами (ядро —
  экран ревью); три отдельных словаря статусов (`STATUS_META` в `EstimateList`,
  `statusLabel()` в `lib/reviewState.ts`, `KIND_LABELS` в `StructureNotice`);
  одна точка захардкоженной локали дат (`Intl.DateTimeFormat("ru-RU")` в
  `EstimateList`); `pluralizeRu` (задел этапа 3) — 3 места вызова.
- **Бэк:** кастомной модели ошибки нет — везде голый `{"detail": ...}`;
  ~30 точек пользовательских HTTP-ошибок в 6 доменах; у 13 доменных исключений
  в `domain/errors.py` **нет общего предка** (все наследуют `Exception`
  напрямую); pydantic-422 до пользователя не доезжает (фронт показывает
  `statusText`); серая зона — персистируемые русские тексты `estimates.status_detail`
  и `estimate_rows.match_error` плюс текстовые `detail` в 202-ответе перезапуска.
- **Показ ошибок:** `detail` бэка течёт в UI напрямую (`client.ts` →
  `err.message` → toast); маппинга кодов нет; fallback-литералы «Не удалось…»
  разбросаны по вызовам.

## 2. Ключевые решения (и почему)

| Решение | Обоснование |
|---|---|
| Охват кодов: HTTP-ошибки + статусы матчинга + pydantic-422 (полный) | Туркоязычный оператор не должен видеть русских служебных текстов нигде. Подтверждено пользователем. |
| Код — атрибут доменного исключения (подход A) | Код ошибки — семантика ситуации, а семантика живёт в домене: `EstimateCompletedError` и т.п. уже существуют. Маппинг «класс → код» на API-слое невозможен: `InvalidReviewActionError` поднимается из 4 точек с разными причинами — код задаётся в точке `raise` (дефолт на классе, переопределение конструктором). |
| Ввод базового `DomainError` — явный пункт работ | Общего предка сейчас нет; миграция всех 13 классов (и замена двух `LookupError` на `EstimateNotFoundError`/`EstimateRowNotFoundError`) — механическая работа по 6 доменам, не «маленькое слово в спеке». |
| Инвариант обратной совместимости | `detail` остаётся человекочитаемым русским текстом с прежней семантикой; `code` — строго добавка. Существующие тесты на тексты не краснеют; фронт мигрирует на коды без флаг-дня. |
| Критерий для серой зоны: персистируется → контент, генерируется в ответе → код | `status_detail`/`match_error` лежат в БД русским/техническим текстом — их не перевести на лету. Замораживаются как диагностика; локализуемый заголовок — по персистируемому машинному коду (`estimates.status_code`, nullable). |
| `match_error` строки — без кода | Произвольный `str(exc)` от LLM-матчера, не enumerable. Ключ локализованного заголовка — сам `row.status == "error"`; сырой текст показывается как диагностика. |
| Accept-Language на бэке — отклонено | Не альтернатива, а другая архитектура с худшими свойствами: словари tr уезжают в бэк, где их некому вычитывать; персистируемые тексты всё равно требуют кодов; фронт обязан иметь i18n для собственного UI — бэк-перевод не экономит словарь, а дублирует его. |
| Выбор языка — `localStorage["ciw.ui.lang"]` | Переживает логаут и закрытие браузера; правило «в sessionStorage только JWT» не нарушается; бэк не трогается. Поле в профиле пользователя — в TECH_DEBT, если операторы начнут мигрировать между машинами. |
| Дефолт — детект браузера | Порядок: сохранённый выбор → язык браузера (`tr*` → tr, иначе ru), `fallbackLng: "ru"`. Туркоязычный коллега с турецкой ОС сразу видит tr; на демо — ru. |
| Два PR | PR-1 (бэк) самоценен архитектурно и не ломает фронт (код идёт рядом с detail); PR-2 (фронт) зависит от PR-1 только маппингом кодов. Один PR нечитаем для ревью (бэк + весь фронт + два словаря). |
| Словари — статическая сборка, один файл на язык | Объём мал (десятки экранных строк); lazy-loading и неймспейс-файлы — преждевременная сложность. |
| Переключатель — только в меню пользователя | На логин-экране не нужен: детект браузера покрывает первый заход, язык применяется и до авторизации. |

## 3. PR-1 — Бэкенд: модель ошибок с кодами

### 3.1 Доменный слой

- `domain/errors.py`: базовый класс `DomainError(Exception)` с классовым
  атрибутом `code: str` и возможностью переопределить код аргументом
  конструктора (для многопричинных классов).
- Все 13 существующих классов переводятся под `DomainError`, каждому — дефолтный код.
- `LookupError`-точки в сервисах (`estimate_review_service`,
  `estimate_export_service`, `estimate_service`) заменяются на новые
  `EstimateNotFoundError` / `EstimateRowNotFoundError(DomainError)`;
  `except LookupError` в роутах — на новые классы.

### 3.2 API-слой

- `api/schemas.py`: модель `ErrorOut { detail: str | dict, code: str }`.
- `api/errors.py` (новый): `HTTPException`-подкласс с полем `code` + хелпер
  `api_error(status, code, detail)`; один exception-хендлер рендерит `ErrorOut`.
- Голые `HTTPException`-литералы в роутах (~10 точек) мигрируют на хелпер;
  `except DomainError`-ветки берут `exc.code`.
- Хендлеры `AuthError`/`DuplicateError` в `main.py` переходят на форму `ErrorOut`
  (заголовок `WWW-Authenticate: Bearer` у 401 сохраняется).
- `DeletionGuardError`: объектный `detail` `{message, force_required, deleted}`
  сохраняется как есть, `code: "template_deletion_guard"` — на верхнем уровне тела.
- Новый хендлер `RequestValidationError`:
  `{"detail": "Некорректные данные запроса", "code": "validation_error",
  "errors": [<массив pydantic>]}`. Массив прогоняется через `jsonable_encoder` —
  в `ctx` pydantic-ошибок бывают несериализуемые объекты (`ValueError`).

### 3.3 Персистируемые статусы (серая зона)

- Миграция: nullable-колонка `estimates.status_code` (TEXT). Порт
  `EstimateRepository.set_status` получает параметр `code: str | None = None`.
- Четыре писателя проставляют коды: `matching_partial_error`,
  `matching_unexpected`, `matching_blocked_dictionary`, `matching_reset_after_crash`.
- `status_detail` не меняется (сырая диагностика). Старые сметы:
  `status_code IS NULL` → фронт показывает `status_detail` как сейчас (фолбэк).
- `EstimateDetailOut` дополняется `status_code`. Элемент списка
  (`EstimateSummaryOut`) — нет: он и сегодня не несёт `status_detail`,
  бейдж списка ключуется по `status`, а баннер живёт на detail-странице.
- 202-ответ перезапуска матчинга: `{"status": "accepted", "code": ...,
  "detail": <прежний текст>}` — коды `match_queued` / `match_already_running` /
  `match_requeued`.

### 3.4 Номенклатура кодов (контракт)

Правило: `<сущность>_<предикат>`, snake_case, без HTTP-статуса в имени
(статус — транспорт, код — семантика). Оговорки к правилу (осознанные, не опечатки):

- **auth-домен** — устоявшиеся идиомы без сущности (`not_authenticated`,
  `admin_required`, `invalid_credentials`, `account_disabled`): общепринятые
  имена читаются лучше искусственных `auth_*`-конструкций.
- **Серии матчинга:** персистируемые статус-коды — префикс `matching_*`;
  транзиентные коды 202-ответа — префикс `match_*`.

## 4. PR-2 — Фронтенд: i18n-механика и словари

### 4.1 Стек и инициализация

- `i18next` + `react-i18next` + `i18next-browser-languagedetector`.
- Детекция: `localStorage["ciw.ui.lang"]` → язык браузера (`tr*` → tr, иначе ru);
  `fallbackLng: "ru"`. `supportedLngs: ["ru", "tr"]`.
- Словари: `src/locales/ru.json`, `src/locales/tr.json` — статическая сборка,
  один файл на язык. Секции: `common`, `nav`, `auth`, `estimates`, `review`,
  `articles`, `statuses`, `structure`, `errors`.

### 4.2 Извлечение строк

- Все русские литералы UI-хрома из ~23 tsx-файлов и non-tsx точек
  (`reviewState.ts::statusLabel`, `client.ts:27`, `estimates.ts:216`,
  `AuthContext.tsx:36`) уезжают в словарь. aria-label, placeholder, title — тоже.
- Три словаря статусов: тексты — в секции `statuses`/`structure`; структуры
  (variant/clickable/тона бейджей) остаются на месте. **Один статус — один
  ключ:** `STATUS_META`, `statusLabel` и грид/полоса ссылаются на одни и те же
  ключи `statuses.*` — никаких `statuses.grid.*`/`statuses.strip.*`-дублей
  с раздельной синхронизацией перевода.
- **Реактивность не-React точек `t()`.** `useTranslation` подписывает на смену
  языка только вызвавший её компонент; результат `i18n.t` из обычного модуля
  при переключении RU→TR не перерисуется сам. Правила:
  - `statusLabel()` переводится на возврат **i18n-ключа** (`"statuses.confirmed"`),
    `t()` зовёт рендерящий компонент — чистая функция остаётся чистой, подписка
    автоматическая, тесты `reviewState` сравнивают ключи, а не локализованные строки.
  - `client.ts` не зовёт `t()` вовсе: сетевая ошибка несёт `code: "network"`,
    текст резолвится цепочкой фолбэков (§4.4) на стороне компонента/хука.
  - Для остальных не-React точек правило: компонент, рендерящий результат
    такого вызова, обязан звать `useTranslation()` хотя бы ради подписки —
    иначе текст не переключится до следующего ре-рендера.
- **Не извлекается:** `lib/mock/fixtures.ts` (тестовые данные), доменный контент
  (наименования работ/статей), экспортные заголовки (живут на бэке, не меняются).
- `lib/useAuth.ts:17` («useAuth вызван вне AuthProvider») — dev-ошибка, не UI,
  не локализуется.

### 4.3 Плюрализация и форматирование

- Нативная плюрализация i18next (ru: one/few/many; tr: one/other) через
  `t(key, { count })`. `lib/plural.ts`, три вызова `pluralizeRu` и
  `plural.test.ts` удаляются.
- Хелпер `formatDate` в `lib`: локаль из `i18n.language` (`ru` → `ru-RU`,
  `tr` → `tr-TR`); `Intl.DateTimeFormat("ru-RU")` в `EstimateList` мигрирует.
  Числа не трогаем (`toFixed(2)` локаль-независим).

### 4.4 Ошибки API

- `ApiError` получает `code?: string`; `client.ts` читает `body.code` рядом с
  `detail` (форма `detail` — без изменений).
- Цепочка фолбэков показа: `t("errors."+code)` если ключ есть → русский
  `detail` с бэка → `t("errors.generic")`. Оформляется хелпером/хуком —
  единая точка вместо разрозненных `err instanceof ApiError ? err.message : "…"`.
- Fallback-литералы «Не удалось…» у вызовов уезжают в словарь. Сетевая ошибка
  (`client.ts:27`) — локальный ключ `errors.network`.
- Баннер blocked/partial_error в `EstimatePage`: заголовок из
  `statuses.{status_code}`, сырой `status_detail` — вторичным текстом;
  при `status_code === null` — текущее поведение (сырой текст).
- Карточка error-строки: локализованный заголовок + сырой `match_error`
  как диагностика.

### 4.5 Переключатель языка

- В существующем `DropdownMenu` в `AppShell`: два пункта RU / TR с отметкой
  текущего, рядом с «Выйти». Выбор → `i18n.changeLanguage` → детектор сам
  пишет в `localStorage`.
- При смене языка (и при инициализации) обновляется
  `document.documentElement.lang` — скринридеры и корректные переносы.

### 4.6 Перевод tr

- Черновик — LLM, с профессиональной сметной терминологией (keşif, poz, metraj).
  Полный `tr.json` без пропусков (fallback ru есть, но цель — полное покрытие).
- В devlog и TECH_DEBT — явный маркер «tr не вычитан носителями»; вычитка
  туркоязычными коллегами — follow-up вне этапа.

### 4.7 Тесты PR-2

- vitest-setup инициализирует i18n с `ru` — существующие RTL-ассерты русских
  текстов продолжают работать.
- **Структурный тест чётности словарей (обязательный):** рекурсивное сравнение
  множеств ключей `ru.json` ↔ `tr.json` + совпадение наборов интерполяций
  (`{{count}}`, `{{name}}`…) в парных строках. LLM-черновик теряет плейсхолдеры
  и ключи молча — фолбэк на ru маскирует пропуск до жалобы оператора; тест
  ловит это в CI и навсегда охраняет будущие добавления («добавил в ru,
  забыл в tr» краснеет).
- Новые: парсинг `code` в `client.test.ts`; цепочка фолбэков (код в словаре /
  кода нет / вообще нет тела); переключатель + персист (включая
  `document.documentElement.lang`); плюрализация ru и tr; `formatDate` для
  обеих локалей; `statusLabel` возвращает ключи.

## 5. Вне скоупа (осознанно)

- Перевод доменных данных и экспортного .xlsx (решение роадмапа §6).
- Переключатель языка на экране логина (детект покрывает).
- Поле языка в профиле пользователя на бэке (TECH_DEBT).
- Вычитка tr носителями (follow-up, вне кода).
- Ретро-заполнение `status_code` для старых смет (фолбэк на сырой текст достаточен).
- Локализация писем/уведомлений — их нет в продукте.

## 6. Риски

- **Объём извлечения строк** (~23 файла) — механически большой; смягчение:
  извлечение по файлам с проверкой typecheck/тестов на каждом шаге
  (subagent-driven, задачи по экранам).
- **Терминология tr** — смягчается вычиткой носителями (follow-up) и
  использованием устоявшегося профессионального словаря в черновике.
- **Рассинхрон номенклатуры кодов** между бэком и словарём фронта — коды
  зафиксированы таблицей §3.4 как контракт; PR-2 копирует их в `errors`-секцию
  словаря; расхождение ловится фолбэком на `detail`.
- **Существующие RTL-тесты** завязаны на русские тексты — если после извлечения
  тексты изменятся хоть на символ, тесты покраснеют; правило: извлечение
  1:1 без редактуры формулировок (редактура — отдельно, вне этапа).
